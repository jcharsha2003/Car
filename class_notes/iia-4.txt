Materialized View Selection – Problem Setting

• Goal: Choose optimal set of views to minimize query cost & storage
• Workload-driven: Queries define candidate aggregates
• Constraints: Storage budget, maintenance cost
• NP-hard problem (set cover / knapsack analogy)

Problem Formulation

Candidate view set V = {v1, v2, …, vm} 

Storage budget S

• Cost model:

QueryCost(q, V') = cost of answering query q using views V' 

Benefit(v) = Σ reduction in query cost if view v is selected

• Optimization:

min ∑ QueryCost(q, V ′) - Cmaint(v') 
V ′⊆V

q∈W

s.t.

v∈V ′

Greedy Heuristic for View Selection

Algorithm (Greedy Benefit/Cost):

Input: Queries W, Candidate Views V, Storage S 

Initialize SelectedViews = {}

While space available do

For each v in V - SelectedViews:

Compute Benefit(v) = Σ cost reduction for queries in W 

Compute Efficiency(v) = Benefit(v) / Size(v)

Choose v* = argmax Efficiency(v)

If Size(SelectedViews ∪ {v*}) ≤ S: 

Add v* to SelectedViews

Return SelectedViews

•
•

Time complexity: O(|V| * |W| * iterations)
Good practical performance but no global optimality guarantee

Why materialized-view maintenance is hard

• A source tuple can affect many derived tuples through joins and GROUP BY.

• DELETEs require knowing the deleted tuple's prior contribution.

• UPDATEs can change join keys or grouping keys, causing delete+insert effects.

• COUNT(DISTINCT), MIN and MAX need richer state than SUM.

• Late-arriving data can invalidate already materialized aggregates.

• Distributed sources may be unavailable when maintenance needs them.

• Concurrent changes can make naïve refresh algorithms inconsistent.

• Source and warehouse transactions may have different commit times.

Full vs Incremental view maintenance — core idea

Naïve

V = Q(R)
After ΔR:
V' = Q(R ∪ ΔR)

Recompute Q over all R.

Incremental

V' = V ⊕ ΔV
// ⊕ denotes the appropriate set/bag 
update operation //
Compute ΔV from:
V + ΔR + auxiliary state.

Incremental Maintenance Example 
View V = SELECT region, SUM(sales) FROM fact_sales GROUP BY region

Goal: avoid scanning 
unaffected R.

Base update: (Delhi, Shoes, 10), Incremental delta: ΔV = {(Delhi, +10)}

Update rule: If Delhi in V: V[Delhi] = V[Delhi] + 10 Else: Insert (Delhi, 10) into V

Full refresh
• Simple correctness model.
• Easy recovery from inconsistencies.
• Cost depends on full source/view size.
• Can create long refresh windows.

Incremental refresh

• Cost depends mainly on changed data.
• Requires delta rules and metadata.
• Can be dramatically faster for small changes.
• Harder for joins, deletes and non-additive 
aggregates.

Self-maintainability

Definition
• A materialized view is self-maintainable 
if it can be maintained at the warehouse 
without accessing all base source data.
• Useful when sources are remote, 
expensive or unavailable.
• May require auxiliary relations stored 
at the warehouse.

Design trade-off
• More auxiliary data → more storage 
and maintenance.
• Less auxiliary data → more remote 
source access.
• Goal: enough information to derive 
exact deltas locally.
• Keys and referential constraints can 
reduce auxiliary data.

Self-maintenance converts network/source dependency into local storage dependency.

View adaptation — a different problem

Maintenance

• Base data changes.
• View definition stays fixed.
• Goal: update V to remain 
correct.

Adaptation
• Base data may stay fixed.
• View definition changes.
• Goal: transform old materialization into 
the new view result.
• Can avoid full rematerialization in many 
cases.

This distinction is easy to miss and is an important research topic.

View adaptation example

V_old = SELECT category,

Old view

SUM(amount)

FROM Sales
GROUP BY category

V_new = SELECT category, region,

New view

SUM(amount)

FROM Sales
GROUP BY category, region

Old V lacks region → cannot 
generally reconstruct V_new.

Lesson: adaptation depends on whether the old materialization retained enough information.

When adaptation is possible

Often possible
• Changing a selection predicate when 
required tuples remain available.
• Changing projection when omitted 
information is stored elsewhere.
• Some GROUP BY changes when finer-
grained state was materialized.
• Union/EXCEPT changes when relevant 
components are retained.

Often impossible from old MV alone

• New grouping attribute was never 
materialized.
• New join requires source attributes 
not retained.
• New predicate needs information 
discarded by projection.
• Semantics changed beyond what old 
state can support.

A materialized view is also an information-loss decision.

Designing MVs as future-proof state

Naïve design
• Materialize only the exact dashboard 
result.
• Minimal storage today.
• Future queries may require full 
rematerialization.
• View redefinition becomes expensive.

Strategic design

• Materialize reusable intermediate 
states.
• Retain keys needed for joins.
• Retain dimensions needed for likely 
grouping.
• Use auxiliary views to support self-
maintenance.
• Optimise the portfolio, not one view.

The best MV design balances today's query speed against tomorrow's 
maintenance and adaptation cost.
