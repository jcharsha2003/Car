Schema matching vs schema mapping

Schema matching asks

• Which elements correspond?

• Does customer_name match client_full_name?

• Can one source attribute map to several target 
concepts?

• How strong is the correspondence?

Input: Two or more schemas Σ1, Σ2, … , Σn.

•
• Output: A set of correspondences:

• M = {(ai, bj , sim(ai, bj )) ∣ ai ∈

Σ1, bj ∈ Σ2}

• Objective: Identify semantically related

attributes, i.e.

sim(a,b) ∈ [0,1]
Match if sim(a,b)≥θ 

Schema mapping asks
• How do we express the correspondence formally?

• What transformation is required?

• Can the mapping be executed?

• Does it require joins, filters, aggregation or 
functions?

• How can queries be rewritten?

Matching is discovery; mapping is an executable semantic relationship.

Semantic Conflicts: NetPrice = GrossPrice – Discount
Representation Conflicts: Date = DD/MM/YYYY vs YYYY-MM-DD

Evidence beyond names
Data types and constraints
Value distributions / examples
Neighbouring attributes
Keys and foreign keys
Table/class context
Business glossary / ontology
Source ownership and provenance

A strong matcher uses names + structure + instances + constraints + context.

Similarity Functions

• Lexical (Linguistic)-based: Edit distance, Jaccard, cosine (token-level), synonym

• Semantic-based: WordNet, ontologies, embeddings. 

• Structural-based: Uses schema tree/graph

•

• Hybrid:

sim(a, b) = α ⋅ simlex(a, b) + β ⋅ simsem(a, b) + γ ⋅ siminst(a, b)

Linguistic/Lexical  Matching

• Tokenization of names

• PurchaseOrder  purchase + order

• Expansion of acronyms

• UOM  unit + of + measure

• Clustering based on keywords and data-types

• Street, City, POAddress  Address

• Linguistic similarity

• Pair-wise comparison of elements that belong to the same cluster
• Token similarity = f(string matching, synonyms score)
• Token set similarity = average (best matching token similarity)

• Thesaurus: acronymns, synonyms, stop words and categories

Example – Linguistic/Lexical Matching

Schema 1: Customer(CustID, Name, Address)
Schema 2: Client(CustomerNumber, FullName, Location)

Similarities:

CustID ↔ CustomerNumber = 0.92 (edit distance). 

Name ↔ FullName = 0.88 (cosine).

Address ↔ Location = 0.73 (Jaccard).

Threshold θ = 0.8 → first two accepted as matches.

Schema-based hybrid matching algorithm

Based on combining multiple approaches that use only schema (no instances)

Input: Two schema graphs
Output: Similarity matrix and candidate mapping

• Linguistic matching: compare attributes based on names, data types, etc

• Use a thesaurus to help match names by identifying short-forms (Qty for Quantity),
acronyms (UoM for UnitOfMeasure) and synonyms (Bill and Invoice). The result is
a linguistic similarity coefficient, Lsim, between each pair of elements.

• Structure matching: compare elements based on the similarity of their  contexts or 

vicinities. The result is a structural similarity coefficient, Ssim,  for each pair of elements.

• Compute the Weighted similarity: Wsim = w * Lsim + (1 – w) * Ssim

• Mapping generation: a mapping is created by choosing pairs of schema  

elements with maximal weighted similarity.

Why should embeddings primarily generate candidates rather than directly decide equivalence?

What should be embedded?

• Attribute name and description.

• Table/schema context and neighbouring attributes.

• Representative data values and distributions.

• Keys, foreign keys and relationship structure.

• Ontology class/property, domain and range.

• Business glossary, source owner and temporal context.

The best representation embeds context, not just the column name.

Embedding representation — example

Weak representation

embed('cust_nm')

Very little semantic context.

Possible candidates:
customer_name
customer_number
customer_status
party_name

Context-rich representation

embed('Attribute: cust_nm
Table: CUSTOMER
Meaning: unique customer name
Type: VARCHAR
Examples: Anil Kumar, Sarah Lee
Neighbours: cust_id, email')

Context-rich embeddings reduce ambiguity because the model sees meaning, type, 
examples and relational context.

Candidate generation with embeddings

Step 1 — vector retrieval

• Encode source attribute as e_s.
• Encode target attributes as e_t.
• Compute cosine similarity:
• sim(e_s,e_t)=(e_s·e_t)/(||e_s|| ||e_t||)
• Retrieve top-k target candidates.

Step 2 — validate/rerank

• Datatype compatibility.
• Value distribution similarity.
• Structural-neighbour similarity.
• Key / foreign-key compatibility.
• Ontology domain/range.
• Cross-encoder/LLM/human review.

Embedding similarity is a retrieval signal—not semantic proof.

Multi-signal matching model

Feature signals
• N = name/description similarity
• I = instance/value similarity
• S = structural similarity
• C = constraint/type compatibility
• O = ontology compatibility

Simple ranker
• Score = wN·N + wI·I + wS·S + wC·C + wO·O
• Weights may be hand-designed or 
learned.
• Use labelled correspondences for 
supervised ranking.
• Evaluate top-1 and top-k performance.

Research question: can the weights be learned across domains without losing 
explainability?

Where embedding-based matching fails

Semantic traps
• Address vs billing_address: related, not 
equivalent.
• Revenue vs profit: related, not equivalent.
• Status: source-specific meaning.
• Course code vs course ID: similar labels, 
different semantics.

Engineering traps
• Poor documentation poisons embeddings.
• Rare values may be uninformative.
• Domain abbreviations may be unseen.
• Model bias/drift changes similarity.
• Thresholds do not transfer reliably.

Use embeddings to accelerate discovery; use domain constraints and evidence to 
establish correctness.
